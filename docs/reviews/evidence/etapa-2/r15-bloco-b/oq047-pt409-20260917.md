## 2. Regra da migration `20260917090000_pt409_stale_version_v1.sql`

Gerada mecanicamente a partir do dump (corpos idênticos aos de produção, `create or replace`):

- (a) `raise serialization_failure using <cláusulas>;` → `raise exception using errcode='PT409',
  <mesmas cláusulas>` e, **só quando não havia `detail`**, `detail='<FAMÍLIA>_STALE_VERSION'` (FORMS:
  `FORMS_STALE_VERSION` para `expected_version mismatch`, `FORMS_COMMAND_CONFLICT` para recibo/comando;
  FORMS_WORKER: `FORMS_WORKER_CONFLICT` para lease/multipart/cleanup). Details existentes
  (`SAI_CONCURRENT_CHANGE`, `CIRCULAR_CONFLICT`, `NOTICE_CONFLICT`) e mensagens são preservados.
- (b) `raise exception using errcode='40001', …` → `errcode='PT409'` com a mesma regra de detail
  (`AGENDA_STALE_VERSION`, `PLAN_STALE_VERSION`, `SUPPORT_STALE_VERSION`).
- (c) handlers dos wrappers de envelope: `when serialization_failure` → `when serialization_failure or
  sqlstate 'PT409'`; `sqlstate in('40001','23505')` → `in('40001','23505','PT409')`;
  `sql_state='40001'`/`p_sqlstate='40001'` → `in('40001','PT409')`. Sem isso, o PT409 interno escaparia
  dos wrappers de Locais/Convites/Instituições/Formulários v2/Estrutura como HTTP 409 em vez do envelope
  200 `SAI_CONCURRENT_CHANGE` que o FE consome — regressão de contrato. A captura de
  `serialization_failure` real do Postgres continua.

Diff por função contra o dump (script `verify-diff` no scratchpad): **202 linhas removidas, 193
adicionadas em 126 funções**; toda linha removida contém `serialization_failure` ou `'40001'` (ou é a
continuação de um `raise` que ocupava duas linhas e foi unido numa); toda linha adicionada contém `PT409`.
Preflight exige `postgres` e a existência das 126 assinaturas; pós-verificação falha se sobrar
`raise serialization_failure` ou `errcode='40001'` em qualquer schema, ou se menos de 126 funções
referenciarem PT409. `lock_timeout 5s`, `statement_timeout 300s`, idempotente.
